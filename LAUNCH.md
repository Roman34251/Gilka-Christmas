# Запуск реальних продажів

## Поточний стан

Вітрина й серверна інтеграція написані. Новий код ще не опублікований. Реальний еквайринг не перевірявся: токен monobank не наданий. База замовлень у Cloudflare не створювалася.

## 1. Контент і реквізити

У Sanity додайте реальні товари для кожної категорії, галереї, опис, характеристики й ціни. Для ікри обов’язково заповніть вид, виробника, склад/алергени, вагу, умови зберігання і строк придатності. Фотографії розділів — атмосферні ілюстрації, не фотографії конкретного товару.

Перед активацією онлайн-оформлення потрібно доповнити інформаційні сторінки реквізитами продавця, затвердженими умовами повернення, обробки даних, строками відправлення та харчової логістики. Поточні тексти — базова інформація, не завершений юридичний пакет.

## 2. База замовлень Cloudflare D1

У Cloudflare → Storage & databases → D1 створіть базу `gilka-orders`. Збережіть її фактичний Database ID. У `wrangler.jsonc` додайте `d1_databases` з binding `ORDERS_DB`, database_name `gilka-orders` і отриманим database_id. Схема таблиці — файл `orders-schema.sql`.

Після створення binding із кореня проєкту:

```powershell
npx wrangler d1 execute gilka-orders --remote --file=orders-schema.sql
```

Це створює таблицю замовлень у конкретній новій базі. У панелі D1 власник акаунта може переглядати замовлення. `payload` містить контактні дані, спосіб доставки та склад кошика; доступ до нього має бути лише у працівників, які обробляють замовлення.

## 3. Післяплата

Коли база готова, інформаційні сторінки доповнені й узгоджена обробка замовлень, додайте Worker variable `ORDERS_ENABLED=true`. Після тестового замовлення перевірте, що запис з’явився в D1, а покупець бачить номер. Без цього прапорця checkout залишається недоступним.

## 4. monobank

Потрібен токен інтернет-еквайрингу з кабінету продавця, а не токен особистого рахунку. Додайте його в Cloudflare → Worker → Settings → Variables and Secrets як **Secret** з назвою `MONO_TOKEN`. Не додавайте токен до Git або JavaScript браузера.

Після цього протестуйте спочатку тестовий токен: створення рахунку, успішну/відхилену оплату, повернення на сайт, webhook і повторне відкриття статусу. Для webhook потрібна доступна HTTPS-адреса. Реальний платіж виконує власник платіжного засобу.

Офіційна документація: https://api.monobank.ua/docs/acquiring.html

`invoice_review` означає, що банк міг створити рахунок, але сайт не отримав достовірної відповіді. Менеджер перевіряє рахунок у кабінеті банку за reference (повний ID замовлення). Не створюйте новий платіж, доки не з’ясовано стан попереднього.

## 5. Нова пошта та ікра

Зараз покупець вводить місто й номер/адресу точки отримання вручну. Це не API-інтеграція Нової пошти, не автоматичний розрахунок вартості й не створення ТТН. Для великих ялинок менеджер перевіряє розміри пакування й придатність поштомата.

Для ікри погодьте пакування, температурний режим і строки перевезення. Лише після цього активуйте `FOOD_SALES_ENABLED=true`. До активації покупець бачить пропозицію узгодити таке замовлення телефоном.

## 6. Фінальна перевірка

Перевірити пряме посилання на товар після перезавантаження, пошук, порожні категорії, зміну кошика, форму на телефоні, запис у базу, фактичну оплату, webhook без повернення покупця на сайт, обробку менеджером і видалення тестових замовлень за погодженим порядком.
